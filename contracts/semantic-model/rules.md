# Semantic Model Rules — M1 identity slice

Contract version: `1.0.0`  
Profile: `m1-project-discovery-1`

## Identity and subject references

A subject identity is the explicit triple `{authority, domainId, localId}`. Its kind is stored beside the identity in `M1SubjectRef`, not encoded in the identity. E0–E4 layer, path, source name, line/byte location, commit, content digest, parser node ID, and graph-tool ID are not identity components.

Within one identity domain, one identity has one subject kind. Reusing an identity with a different kind is a contract error; the validator preserves the conflicting records in its diagnostics rather than silently rewriting the kind. A path or name may be used as evidence or a lookup key, but cannot by itself establish identity.

`M1Registration.sourceKey` locates a source declaration within the fixed input and acquisition profile. It is not emitted as the subject identity. Calling `register_m1` again with the same domain, source key, and kind returns the existing identity and unions evidence IDs. Reusing that source key with another kind or domain returns `CONTRACT_INVALID`; the registry must not guess continuity or allocate a replacement identity.

A new registration receives an explicit UUID local identifier under authority `c2s-local` and the caller-provided identity domain. Moving a checkout, adding evidence, or resolving a project-boundary assessment does not re-key the subject. M1 references carry no context reference; contextual interpretation uses the separate `semantic-fact-model-1` profile. There, `contextRef` annotates a reference without changing its identity. Contexts are partial assignments over registered finite Boolean or enum keys; absent keys remain unconstrained. Fact conditions and subject/value contexts are checked together. Contradictions are errors (`CTX_CONTRADICTION`); unsupported conditions, unknown keys, and over-budget searches remain explicit gaps. Single-valued claims conflict only when their conditions can overlap; unsupported overlap yields `POTENTIAL_CONFLICT`.

## Structural validation boundary

`validate_model` runs four dependent stages in order: fixed catalog integrity, versioned wire structure, internal subject/evidence references, then the available M1 invariants. A failed stage leaves its dependent stages `not_run`; reference diagnostics retain identity/source conflicts and related record references. `valid` reports contract errors only. Different values for a single-valued predicate in the same subject/claim-mode/condition are preserved as paired `conflict` diagnostics and return `valid=true`, `consistency=conflicting`; otherwise a successful checked subset has `invariants=partial`, `consistency=undetermined`. Neither result establishes source truth, project ownership, semantic completeness, or runtime behavior. Evidence-source observation checks and broader cross-fact rules remain outside this M1 slice.

## Project-boundary assessment invariants

An assessment declaration must reference a `SourceDeclaration`, and every candidate must reference a `Project`. `resolved` has exactly one candidate, `ambiguous` has at least two, and `unresolved` has none. An assessment may supersede only assessments with the same declaration identity and `ruleId`; the in-bundle supersedes graph must be acyclic. These constraints validate explicit assessments only: package or workspace membership does not infer project ownership.

## Dependency requirement and resolution records

The `semantic-fact-model-1` profile can retain `dependencies` separately from `dependencyResolutions`. A requirement records its consumer, purpose, stage, path/version selectors, condition, and evidence; resolution records candidates/status, configuration, visibility, and `scopePosition`. `scopePosition` is independent of dependency identity and resolution status. Providers and consumers must resolve to registered subject identities. A resolved record has exactly one provider, ambiguous has at least two, and unresolved has none. Requirements remain present when no resolution exists. This initial contract does not infer requirements from package metadata or decide whether a project-level dependency cycle is an error.

## Evidence and coverage invariants

`source_observations` is caller-supplied and is never obtained by reading files or contacting a network. A missing observation or `unchecked` status yields a `gap` diagnostic and does not make the contract invalid. `verified` requires an observed SHA-256 equal to the evidence digest; `mismatch` requires an observed, different digest and produces an `INPUT_MISMATCH` contract error. Observation entries must be unique and reference evidence in the bundle. A coverage record marked complete cannot carry gap/error diagnostics or cite unchecked evidence. In-bundle coverage supersedes links must preserve selector and subject identity, resolved diagnostic keys use compact JSON `[code,recordId,path]` values referring to gap/error diagnostics on a superseded record, and lineage must be acyclic.

Full-profile `semanticStates` keep presentation (`ref_only`/`expanded`) independent from acquisition (`obtained`/`not_acquired`/`unsupported`/`not_applicable`) and from the fact claims themselves. An obtained `ref_only` state may point at facts without expanding them. Not-acquired/unsupported states cannot claim facts and require a gap diagnostic; not-applicable requires a reason and evidence; acquired facts must match the state's optional subject/predicate scope. These state records report what the caller says was acquired and shown, not completeness outside their declared selector and coverage.

In `semantic-fact-model-1`, facts can distinguish `declaration`, `specification`, `static_may`, `static_must`, `observation`, and `interpretation`; these modes are not ranked as truth. `evidenceRefs` attach each evidence ID with a `Supports`, `Refutes`, or `Limits` role. Optional derivations name a rule and premise fact IDs; missing premises are reference errors and derivation cycles are invariant errors. Neither support role nor derivation establishes source truth. The M1 project-discovery profile remains limited to declaration/interpretation and unqualified evidence IDs.

Negative claims require a `negativeBasis` using `enumerated_input_membership` or `registered_catalog_membership`, with a nonempty input ID set, one result per input, the same condition as the claim, human review, no unresolved gaps, and no matching inputs. This validates that the submitted closure record is internally complete; it cannot prove the declared input list is actually exhaustive. An observed match contradicts the negative claim, while missing review or inputs remains an error/gap rather than evidence of absence. M1 does not accept negative claims.

## Finite condition reasoning (implementation slice)

`src/c2s_semantic_contract/conditions.py` supports `true`/`false`, `eq`/`neq`, `all`/`any`, and `not` over caller-declared finite Boolean or enum domains. It exhaustively checks up to 4,096 assignments and returns a witness for `sat`; unsupported expressions, unknown domains, malformed domains, and larger products return `undetermined`, never `false`. `classify_claim_overlap` distinguishes disjoint conditions, confirmed conflicting values, and potential conflicts. The full profile applies condition reasoning to the current syntax-fact, dependency, project-mapping, and build-target ownership rules. Source language conditions are not yet extracted, and several catalog predicates have not yet been added or implemented. The bounded solver does not prove behavior semantics.

`evaluate_condition` separately evaluates an expression under a partial assignment using three-valued Kleene logic (`true`, `false`, `unknown`); missing keys and unsupported source expressions remain unknown, with the reason retained. Empty `all` is true and empty `any` is false. Evaluation and exhaustive satisfiability are distinct operations.

`validate_model` builds configuration-separated candidate graphs from explicit dependency resolutions and reports cycle analysis separately in `dependencyCycles`; a possible project cycle is not itself a contract error or a build-rule violation. `diagnose_conditional_cycles` enumerates simple directed cycles and evaluates each cycle's edge conditions jointly. It returns possible cycles with witnesses, infeasible cycles after exhaustive finite-domain reasoning, and undetermined cycles with reasons; the original graph is returned unchanged. Enumeration is bounded by 4,096 cycles and a bounded search budget; exhaustion is an explicit gap and leaves unvisited cycles unknown.

## Language-mechanism boundaries in algorithm lowering

The current Python/Rust lowering is a syntax projection. Rust macro invocations remain source-located `opaque` steps; macro expansion and `cfg` selection are not performed. Python decorator expressions are kept out of function-body steps, with wrapper/callback replacement semantics reported as omissions. Python lambda and Rust closure source spans remain visible, but anonymous bodies are not lowered as independent algorithms and capture/binding behavior remains unknown. These records preserve a boundary and do not represent generated, selected, or captured behavior as established facts.

The algorithm contract exposes `project_algorithm(document, algorithm_ref)` to render recorded steps/edges and `check_source_coverage(document, checklist)` to validate reviewed checklist mappings to steps/effects or explicit gaps. Checklist items without review or whose mapped step/effect is missing remain uncovered. These functions do not read source, verify that a checklist is exhaustive, or prove the text equivalent to implementation. Fixed human-reviewed source checklists for Rust/C++/Python acceptance cases remain a separate requirement.

## Query-result projection boundary

`project_query_to_semantic_model(query_result)` maps every currently supported acquisition kind to the full-profile catalog and retains the original kind, E-layer, owner, source text, and evidence-inclusion flag in `sourceMetadata`. It derives deterministic identities for the emitted bundle only; these are scoped to the input query and do not establish identity continuity between checkouts. Source-file digests are independently re-read and compared before their evidence is marked verified. Workspace membership remains unchecked unless the query supplied a verified native-tool observation. Query gaps and selector coverage are preserved; an empty result is not treated as proof of absence. The projection covers the analyzer's current finite kind set, not every semantic predicate that could exist in a project, and does not increase acquisition completeness.

`project_algorithm_to_semantic_model(algorithm_document, project_root)` maps source-located algorithm steps, regions, body links, control edges and data edges to typed full-profile facts. Algorithm lowerers include the input file SHA-256; projection rejects stale or out-of-root spans and verifies every emitted evidence digest. Algorithm-local implementation identities are deterministic within this projection and are not silently merged with declaration identities from a separate query bundle. Opaque steps, algorithm omissions and unmapped spans remain coverage gaps; this projection does not prove that the extracted algorithm covers every source behavior.

The expanded full-profile subject vocabulary adds `BehaviorBody`, `BehaviorRegion`, and `BehaviorStep`. `program.contains` (E2), `behavior.has_body` (E4), and `region.member` (E4) are distinct typed associations/compositions; they do not imply `refines`, project ownership, or implementation equivalence. `region.member` points to a `BehaviorStep`, while algorithm-body schema references remain their own contract. M1 keeps its four-kind subject vocabulary.

The E1 catalog also distinguishes `BuildTarget`, `BuildRecipe`, `BuildAlias`, `OutputSpecification`, and `ArtifactObservation`. `build.declares_target` and `build.declares_recipe` keep native targets separate from language-level recipes; overlapping claims that one target belongs to different Projects are errors, while disjoint conditions are preserved. `build.alias_of` does not create another target and must resolve to a target declared in the submitted fact set. `build.declares_output` does not claim that a build happened; `build.observed_artifact` requires `observation` claim mode and at least one evidence item that is a verified tool output. These are typed record relations only; the current source analyzer does not infer them from arbitrary build systems.

E3 contracts distinguish `contract.precondition`, `contract.outcome`, `contract.effect`, and `contract.ordering`. Their text values remain claims with explicit claim modes and evidence; they do not imply runtime checks, observed results, actual effects, or total execution order.

E4 now distinguishes implementation links, call edges, binding introduction, capture, reads, writes, algorithm description, and pseudocode projection. Provenance `generated_from` is separately classified without a primary semantic layer. The binary `behavior.captures` relation does not encode capture mode, and the other catalog entries do not claim the analyzer currently extracts those edges.

E0/E1 catalog entries now include project-boundary declarations, coordination-group membership, usage requirements, entry binding, build-task ordering, dependency requirements, and provider candidates. The catalog keeps these concepts typed and distinct, but only the existing dependency requirement/resolution records currently have conditional resolution validation; these new predicates do not yet implement build-system acquisition or multi-candidate structured arguments.

Full-profile predicates with more than a subject/value pair use named `arguments` records. The subject is still a registered identity; each argument role is uniquely declared by the predicate catalog and independently type-checked and reference-checked. Facts with arguments set `value` to null; binary facts retain their current value form. M1 remains binary-only. This permits call-site/callee/dispatch and closure/binding/capture-mode claims without encoding several roles into one string. Variable-cardinality candidates and nested facts remain unsupported.

Algorithm projections link the implementation to a `BehaviorBody` with `behavior.has_body`, the body to regions with `behavior.body_region`, and each region to steps with `region.member`. Control edges separately connect step identities. This avoids assigning a shared algorithm step to an arbitrary first implementation when one description has multiple implementation references.
