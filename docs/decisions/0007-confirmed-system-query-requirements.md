# ADR-0007：查询与分析系统需求确认

状态：用户明确确认。日期：2026-11-02（Asia/Shanghai）。

## 用户确认原文

1. 分层语义事实，当然是应该能逐层查询项目的语义事实，如项目级的，类型级的，函数级的，等等，比如，项目中都有哪些类、某个类的成员都有哪些、哪个类的哪个成员是如何定义的、函数是如何定义和实现的，等等。但要注意的是，按前面的讨论，每次仅返回一层的完整事实，不递归展开。
2. 用户指定存储目录后，目录中的都是要分析的。
3. 查询结果的消费者既有用户也有其它Skill，所以，既需要人可读的报告，也需要机器可读的结构化数据。
4. 用户查询指定目录中项目的语义事实时，如果尚未分析，那就针对用户的查询请求开始分析。对同一主体的多次查询只是补充当次请求中尚未完成分析的内容。
5. 遇到缺口要如实报告，并说明原因。
6. 允许执行哪些分析操作，这看你的设计而定。只要是能提取到需要的语义事实，分析操作都可以执行。
7. 当前无法严格定义结果的正确性，如实报告就可以。如果用户有要求，但获取不到语义事实时，明确告知。性能和Token优化，你可以通过优化前后，自行对比来看。

用户随后补充：“当前一层指的是符合用户请求要求的顶层语义事实。”

## 对既有基线的明确修订

- “完整”限定于本次请求要求的顶层语义事实；“最小”只限定响应范围，不授权任意删减该范围内所需事实。
- 不将本次顶层等同固定E0–E4编号、目录层级或主体类型。项目有哪些类、类有哪些成员、成员定义和函数定义/实现均按实际请求定位顶层。
- 旧的按深度递归呈现示例改为按明确请求选择目标，返回该请求的顶层事实；更深组成/关联不递归夹带。ADR-0002的原始确认记录保留，当前行为以本次明确说明为准。
- 指定目录内内容皆为分析范围，不等于查询前预构造目录内全部语义。范围内嵌套项目、测试、示例等不能仅因目录类别被静默排除；取不到时报告原因。
- 面向用户与其他Skill提供可读报告和结构数据；同主体后续查询复用已取得内容，仅补本次未完成部分。
- 必要分析操作由设计安排，不逐操作重新索取同一授权；仍遵守单次分析项目不变前提及实际环境权限。本次确认没有启动产品实施或当前运行项目分析。
- 不以严格语义正确性证明、人工完备金标或固定数值SLO作为当前前置。要求如实报告结果、缺口和原因；性能/Token由代理做优化前后对照，不能通过隐去所需事实或缺口伪造收益。结构/引用/公共契约检查仍是技术验证，不能冒充语义正确性证明。

## 权威边界

以上为用户确认的系统需求。工具版本、查询契约编码、目录枚举/身份定位、两种输出生成方式、测量实现等由代理继续设计并标记为设计决定；不要求用户逐项替代理选择。D01的具体技术能力矩阵转为设计/调查事项，D02的评价方式已明确；不能再把它们列为当前等待用户给定金标、负载或毫秒值的阻塞。

整体设计/实施计划仍需技术收敛及用户整体审核；产品开发未批准，不自动归档。跨次来源更新和语句级事实粒度未由本次确认新增，不重开已延期问题。
