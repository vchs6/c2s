# ADR-0010：双向独立编写与确定性CI

日期：2026-11-03。状态：用户确认的目标质量模式；是否具备隔离按实际证据判定。2026-11-05用户通过ADR-0011明确放宽其作为开发启动门禁的要求。

## 确认依据

- U01：用户明确原始问题是“防止编码角色参考测试用例来编写代码，或者是测试用例的编写者，看着代码来编写测试用例”。
- U02：解释AI负责设计/编写/审核/必要诊断，CI负责固定执行、权限控制和证据留存后，用户要求“那就按这个模式完成开发环境的搭建”。
- ADR-0008/0009中的真实项目、职责独立、持续开发授权和禁止自动归档继续有效。

## 已确认边界

目标模式仍保护编码与独立验收作者的双向信息边界，以及工件所有权和独立判断。五种职责仍保留，不要求五种职责彼此无法读取所有工件。审核可读取实现，执行与验证可读取任务所需的实现、用例和证据。按ADR-0011，此目标模式不是开始或继续开发的通用门禁；未具备隔离时可在共享环境推进，但必须报告实际访问限制，不得将其称为盲编写或独立私有验收。

独立作者读取公开需求、契约和作为分析输入的真实Rust/Python项目；不能读取待验收的c2s实现、实现讨论或推导内部实现的私有诊断。编码读取公开需求、契约、设计及开发材料，不能读取独立验收用例、断言、历史或泄露内容的日志。公开Requirement/Scenario不是私有用例。

构建、工具安装、固定测试运行、版本与摘要核查由确定性程序完成，无需每次调用AI。AI负责需判断的设计、编写、审核和必要诊断；不以AI自述代替CI证据，不以调整测试期望迁就实现。CI是否调用模型不是测试独立性的判据。

## 委托内技术选择

沿用现有GitHub托管Linux CI和固定快照/容器边界，不再搭建嵌套Codex。先运行公开合成标记与交接检查，再启用真实角色入口。共同需求按固定版本交给双方，独立产出固定后由CI组合。固定runner不取得模型密钥；模型入口的认证和工具权限另验。当前共享原生工具不能冒充受限的正式双向角色。

历史五角色全隔离试验保留为基础设施证据，不再作为用户要求扩大化解释；实际双向边界与版本交接仍不可省略。公开probe通过不代表真实AI角色已部署或产品已验收。
