# ADR-0013：采用非 DDD 的上游源码事实模型

状态：Accepted（由用户于 2026-11-08 明确要求形成此决策）。

## 背景

C2S 的目标是从上游软件源码及少量说明材料中提取、组织和查询可追溯的项目事实，保留上游项目与模块组织、语义实体及其关系、核心算法和实现方式等参考信息。现有决策将 DDD 作为领域模型设计依据，但 DDD 的聚合、值对象、领域服务、限界上下文及架构层次并不是这些上游事实本身，也不是项目输出目标所必需的概念。

此前的实体中心模型已将语义实体、属性、关系、证据、源码构造、实现映射和测试关联作为事实表达内容。本决策取消其 DDD 方法论约束，不取消用户确认的语义实体模型，不等于回到以类、函数等源码语法类别组织全部事实。

## 决策

### 1. 项目目标是上游事实提取与呈现

C2S SHALL 从源码、项目清单、测试、少量说明文档及可用分析工具中提取并组织上游事实，重点保留：

- 上游项目、工作空间、模块及其可证实的组织关系；
- 项目内可查询的语义实体、实体属性及实体之间有证据的关系；
- 数据与计算实体对应的源码构造、实现方式及核心算法参考；
- 测试实体与其可证实的验证目标、测试入口之间的关联；
- 每项事实的来源、取得方式、支持状态、覆盖状态及未解决缺口。

C2S MUST NOT 生成目标语言迁移方案或目标设计决策；MUST NOT 评价上游哪些组织或设计“值得迁移”；MUST NOT 将源码中出现的实现机制转成目标实现的必要要求；也不负责解释上游为何采用特定架构或组织方式。

关于项目目的、能力、需求或意图的陈述，只有在来源直接表达时才可作为来源事实记录。由源码结构、算法或测试推导出的解释必须标为有证据支撑的分析主张，并保留其依据、状态与未决性；不得仅凭类名、函数名、目录或工具置信度宣称已确认项目的确切需求。

### 2. 语义实体是项目事实模型概念，不是 DDD 实体

“语义实体”表示上游软件中可独立查询、引用或关联的软件概念；项目和模块也可以作为语义实体。该术语不承诺采用 DDD Entity、聚合根或任何特定对象生命周期模型。

数据实体、计算实体、模块及其他实体的属性和关系，按上游证据及查询需要表达。属性是所属实体的描述字段；仅在需要独立查询、引用或表达关系时，才建模为独立子实体。该选择不依据 DDD 值对象、聚合边界或事务一致性规则。

语义模块表示被分析项目中可由证据支持的软件组织概念，不自动等同于 DDD 限界上下文、源码目录、语言模块、Cargo package 或代码图社区。上述来源结构可作为实现参考或组织证据，只有存在相应依据时才与语义模块关联。

### 3. 源码构造是事实来源与实现参考

类、结构体、接口、字段、方法、函数、枚举、泛型、宏、注解、Lambda、闭包及其他语言构造，首先作为带来源位置的源码构造或实现机制记录，不因其语法类别自动成为语义实体。

源码构造可以通过有证据、可追溯的映射，关联到语义实体、实体属性或关系，说明其声明、实现、表示、约束、生成、调用或验证角色。一个语义实体可以由多个构造实现，一个构造也可以参与多个语义实体；映射不确定、部分或缺失时，保留构造和缺口，不伪造映射。

E0 工程组织与协作、E1 构建装配与交付、E2 程序结构与接口、E3 操作行为契约、E4 实现算法与局部语义继续作为可选事实观察视角，用于区分事实内容。它们不是 DDD 架构层、语义实体类别或强制包含层次；不得单凭视角顺序推导实体归属、父子关系或业务边界。

### 4. DDD 与六边形架构不是项目约束

C2S 的领域模型和产品输出 MUST NOT 以 DDD 术语、概念分类或建模方法作为前置约束；不要求创建聚合根、DDD 实体、值对象、领域服务、仓储接口或限界上下文。

C2S 的实现架构也不预先要求采用 DDD 分层、六边形架构或特定存储组织。实现结构按实际工具组合、数据流、测试性和维护成本选择；仍须遵循 OpenSpec 规格管理、Superpowers 工作纪律及已确认的独立审核和验证要求。取消 DDD 不取消这些工程流程约束。

## 考虑过的方案

1. **继续以 DDD 作为项目领域模型方法。** 可沿用既有术语，但会继续把不属于上游源码事实的聚合、值对象和边界带入产品模型，不能直接回答用户的事实提取目标，故不采用。
2. **退回纯源码结构或代码知识图谱。** 可复用 AST、符号和调用图工具，但无法单独表达语义实体属性、来源证据、解释状态、测试目标关联和完整性缺口，故不作为 C2S 的完整目标。
3. **采用非 DDD 的上游源码事实模型。** 以项目事实、语义实体、属性、关系和证据为输出；将语言构造和分析工具结果保留为来源或实现参考。此方案与用户当前目标一致，故采用。

## 对既有决策的影响

- 本 ADR 精确替代 ADR-0001 中“本项目按 DDD”及 DDD 作为事实模型设计依据的表述，并替代 ADR-0002 确认矩阵 B03 中“DDD 用于统一语言、身份及不变量”的建模约束。ADR-0001 采用 E0–E4 五种事实尺度的记录仍保留，但按本 ADR 作为可选观察视角理解。
- ADR-0012 关于语义实体、实体属性、类型化关系、证据、源码构造、实现映射、测试关联和实体详情查询的决策继续有效；其 DDD 依据不再适用。ADR-0012 关于旧、新存储档案兼容迁移的技术决策与是否采用 DDD 无关，维持现状。
- ADR-0003 至 ADR-0011 中与领域建模无关的语言、平台、工作模式、授权、独立交付和发布约束不变。
- 现有 OpenSpec 主规格、活动提案、领域基础说明和提案对齐报告尚未按本 ADR 同步；它们须在下一阶段逐项审查和更新。本 ADR 不代表这些文档或产品实现已完成重构。

## 后果

后续规格需围绕用户请求的上游事实范围定义查询目标、属性、关系、实现参考、来源和覆盖；避免把 DDD 概念作为产品结构。工具矩阵和解析器只需提供事实构造所需的输入，不以采用何种 DDD 聚合或架构层选择工具。实体模型及既有提取器、存储、查询和算法实现需按新目标评估后保留、改造或退役，不据本 ADR 预设整体重写。
