# 非商用源码分析工具调研与 C2S 继续性判断

调研日期：2026-11-08

项目范围：C2S 已确认的源码事实提取目标——保留上游项目/模块组织，提取语义实体、实体关系、函数实现参考和算法伪代码；保存来源证据，支持按需查询并如实报告覆盖缺口。C2S 不负责决定迁移方案，也不解释上游为何采用某种组织方式。

## 结论

**C2S 有继续做下去的理由，但不应继续重复建设通用代码分析器。**

开源工具已能很好地解析源码结构、建立符号/调用图、查找定义和呈现代码片段。若目标只是“浏览项目结构、查某符号、追调用、看函数源码”，CodeGraph、Code Review Graph、Serena 或语言服务器已经提供了现成路径，C2S 没必要再自建一套同类能力。

仍未被本次调查发现由单个非商用工具直接满足的部分，是把这些低层输出整理为**项目自己的、跨语言的、保留来源的语义事实集合**：明确实体及其关系；把项目清单、源码、测试和少量说明文档作为不同证据来源；呈现函数算法参考；在查询范围内区分完整、截断、未解析和未覆盖；给出稳定机器结构及可读报告。现有工具可成为事实来源或适配器后端，但它们的代码图/搜索结果本身不等同于这套事实契约。

因此，建议继续 C2S，定位为轻量的**事实契约、证据归一、覆盖诊断和查询层**，复用成熟解析器及图工具。只在工具没有提供必要事实或无法保证所需覆盖时，才编写语言专用提取器。下一阶段的成败标准应是：固定真实项目上，选用工具的组合能否以更低维护成本，满足 C2S 已确认的事实查询契约，而不是新增多少解析器或图节点。

## 调研方法与边界

先从本仓库既有需求 N01–N09 和真实项目实验开始，需求包括工程/工作空间、声明枚举、实体成员、定义/引用/调用线索、局部算法与函数源码、枚举完整性/截断诊断、按需查询成本，以及 Rust/Python 路径范围。然后核验非商用工具的公开仓库说明、接口与许可证，并对最可能覆盖多项需求的 CodeGraph 1.6.2 做了真实索引试验。

真实试验使用隔离于 `/tmp` 的源代码副本，未改动本仓库或 Click、regex 的原始工作副本，关闭 CodeGraph 遥测。试验固定输入为 Click 提交 `2247b35ea1c47c727d7a06e51fa280e12a863ff6`、regex 提交 `94ac45b2a6e7b1c30927feb5b66c5ded5b7ad447` 及本仓库当时的 `HEAD`。本次试验验证了索引范围、统计、搜索和函数源码/调用链查询；它不是完整性认证、语义准确率基准或性能/Token 对照实验。

许可证按所用组件区分。“开源项目有商业版”不代表本调研采用了商业版：Semgrep 只评估 LGPL-2.1 的开源 CE；没有使用付费规则、托管服务或商业接口。GitNexus 的 PolyForm Noncommercial 许可证只允许非商业使用，单独列出，不作为可广泛复用的默认依赖。CodeQL 等许可/商业条款有额外限制的候选不纳入选择。

当前会话可用的分析类 Skill 清单中没有专门的项目源码事实提取 Skill。Superpowers 是开发流程 Skill，不是代码分析器；Code Review Graph、GitNexus 等仓库附带的 agent Skill 是其自身工具的导航提示，有限提示文本不能替代底层完整数据，也不自动成为 C2S 运行环境中的可调用 Skill。

## CodeGraph 真实项目试验

通过 npm 在 `/tmp/c2s-market-evaluation/npm` 安装公开包 `@colbymchenry/codegraph`，版本 `1.6.2`。索引放在三个临时副本的 `.codegraph` 目录。查询命令及能力如下：

| 输入 | CodeGraph 索引结果 | 对照与解读 |
| --- | --- | --- |
| C2S 当前检出源码 | 88 个索引文件：62 Python、26 YAML；267 function、344 method、54 class、3550 edges | 覆盖了这份检出中的 Python 与 YAML 文件；本身没有把 Markdown 需求/设计文件建模为事实，也没有纳入非目标文件的语义说明。 |
| Click 固定提交 | 100 个索引文件：91 Python、9 YAML；1408 function、489 method、181 class、7775 edges | Python 文件数与仓库原生文件盘点一致；可提供明显超出语法树的符号和关系导航。 |
| regex 固定提交 | 233 个索引文件：227 Rust、3 C、3 YAML；1102 function、3335 method、460 struct、84 enum、430 enum_member、27291 edges | Rust 文件数与原生盘点一致；也发现 C/YAML 文件。但图包含哪些声明和边，不自动证明项目中每种声明或边均无遗漏。 |

在 regex 中搜索 `canonicalize` 得到带 kind、限定名、文件、行号和签名的多个候选；对 `ClassQuery::canonicalize` 取节点后，工具返回原函数源码和调用链。这证明 CodeGraph 对“定位函数、阅读源码、导航调用”很有用，也直接说明伪代码/算法解释仍需 C2S 自己生成或由明确的事实构造逻辑完成。

公开 CLI 有 `files --json`、`status --json`、按文本查询的 `query --json`、`node`、`callers`、`callees` 和 `explore`。本次状态输出明确报告索引状态 `complete`，但该状态只代表工具自己的索引过程完成；CLI 文档没有给出与 C2S 查询范围等价的“返回全部语义实体及遗漏数”事实接口。本次 `query` 实验也表现为检索候选，而非给出全项目所有符号的稳定分页接口。因此，C2S 仍需独立核对输入文件盘点、索引版本/新鲜度、顶层枚举和输出截断。

此前本仓库对 Code Review Graph 2.3.9、Python AST、Tree-sitter 和 Cargo metadata 已有 Click/regex 真实输出记录。其结论同样是：本地语法提取能枚举声明候选；CRG 能提供额外调用/依赖候选，但建图范围受 Git 文件范围影响，且对图新鲜度/完整性仍有缺口；Cargo metadata 的 `--no-deps --offline` 不能当成完整依赖解析或构建产物观察。详细输入、输出和限制见本目录下 `acquisition-survey-2026-11-02/experiment-results.json` 与 `report.md`。

## 对 C2S 当前定位的判断

市场工具已经覆盖“抽语法、找符号、建边、搜代码、读源码”这条低层路径。C2S 的差异必须落在输出，而不是“也有一个代码图”：

1. 以用户定义的语义实体和关系组织事实，实体属性一次性可查，子实体可按请求展开；不直接把类、枚举、宏等语法构造当成语义事实类别。
2. 同时保留源码事实与其语言特定实现参考；算法/伪代码可追溯到源码位置，测试实体可关联被测实体，但不把代码图边当作行为证明。
3. 将清单、源码、测试、文档和外部分析工具结果视为可辨认的证据来源；保留工具版本、输入范围、原始证据、直接/推断/未解析区别和覆盖缺口。
4. 对用户请求的范围提供可验证的顶层完整性、结构化结果和可读解释；不让 top-k 搜索或工具内部“索引完成”冒充事实集合完整。
5. 只补工具无法提供的东西。譬如继续保留 Rust/Python 原生语法/清单适配器，但把跨文件图作为可替换来源，而非必须自研的核心资产。

若目标退化为 agent 的代码导航/源码问答，建议停做 C2S 专用事实仓库，直接使用 CodeGraph 或 Code Review Graph 等开源工具。若目标仍是跨项目、跨语言、可查询并带证据和覆盖说明的上游语义事实集，则继续做 C2S 有必要；没有检索到一个现成开源工具可以直接满足整份契约。

## 建议的后续止损/验收条件

继续投入前，用固定真实项目、固定文件清单和独立预期结果做一次窄范围对照：

- 先定义一批实际需要查询的语义实体/属性/关系和算法事实，不把“图里有节点”当正确答案。
- 比较 C2S 原生前端、CodeGraph/CRG、语言服务器/SCIP 的最小组合，记录每个输出字段对应的工具和源码证据。
- 单独测量全量声明枚举、调用关系准确性、跨语言支持、文档/测试关联、索引新鲜度、失败/截断诊断、冷/热查询成本及实际 Token；区分工具自身数据构建成本和按需查询成本。
- 如果一个现成工具组合能直接满足 C2S 的机器契约、证据追溯与范围完整性，删除相应重复提取代码，C2S 只保留查询门面或停止开发。若只满足导航/图查询，保留 C2S 作为事实归一与证据层，并公开列出仍未覆盖的事实。
- 不以支持更多语言、生成更多伪代码文本、迁移方案生成或商业产品功能作为首期扩张依据。

本报告建议**有条件继续**，不是对当前“完整语义分析器”能力的验收，也不是对任何工具组合的完整性担保。此前记录显示 C2S 产品范围仍有未完成任务，市场调研本身不能将这些任务视为已完成。
