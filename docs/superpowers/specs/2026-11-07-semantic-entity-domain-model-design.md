# 语义实体中心领域模型重构设计

状态：设计草案，等待用户审阅。仅设计；未改产品实现。

## 意图

把项目分析的首要结果从源码结构分类改为项目语义实体及其关系，使查询能够回答项目/模块定义了哪些数据实体和计算实体、实体有哪些完整属性、由哪些源码构造实现、由哪些测试验证。类、枚举、泛型、宏、注解、λ 匿名函数等仍然重要，但只作为实现构造或机制及语义映射证据。

## 模型对象

### 语义实体（`SemanticEntity`）

可独立识别、复用、关联或查询的项目概念。每个实体具有由持久实体注册表分配的 `EntityId`、类型、语义名称、别名、描述和支持它的事实/证据。首期实体类型包括：

- `Project`：项目本身。项目对其定义或包含的语义实体有显式关系。
- `Module`：按职责组织实体的语义模块；不等同于目录、Rust软件包、命名空间或服务。
- `Capability`：项目提供的能力或业务职责，可跨模块组合。
- `DataEntity`：项目创建、读取、维护或交换的信息概念。
- `ComputationEntity`：项目执行的计算/业务操作或能力。
- `ExternalActor`：与项目交互的用户、系统、设备或外部服务。
- `TestEntity`：具有场景、断言或验证目标的测试对象。

类型目录首期有受控常用类型并允许明确登记扩展类型；未知类型不能降格成任意字符串来绕过校验。类型不是源码构造枚举。

### 实体属性（`EntityAttribute`）

默认是实体自身描述中的值对象，不创建独立语义实体身份；被明确引用、跨实体复用或具有独立生命周期时才可提升为实体。属性包含：语义名称与别名、语义类型、值域、基数/可选性、约束、来源证据及实现参考。语义类型和值域分开：`String` 是实现类型证据，不足以推出“订单号”或其有效格式。

值域可记录已证明的有限集合、区间、格式/谓词约束、引用类型或未知/不完整状态；同时标明根据什么证据得到，以及属于声明允许域、代码校验域、规范要求还是运行观察。有限样本不代表完整域。

若属性引用独立数据对象（例如订单的客户），以指向 `DataEntity` 的类型化关系或属性引用表达，不复制子实体完整描述。单实体查询默认完整返回自身全部属性，但不递归返回关联实体全部属性。属性默认由拥有实体身份和稳定槽位键定位；提升为独立实体时保留`promoted_from_attribute`映射，原引用经校验后更新而不复制语义主张。

### 语义实体关系（`EntityRelation`）

带身份引用的有类型有向关系，至少包括：`defines`、`groups`/`contains`、`belongs_to`、`depends_on`、`uses`、`produces`、`transforms`、`interacts_with`、`realized_by`、`verified_by`。关系目标可为语义实体或带身份的行为/属性主张；谓词目录定义允许的端点类型。每条关系有适用条件、证据、覆盖状态；关系词的主客体种类与约束在谓词目录登记。源码目录包含不自动成为 `contains`，函数调用也不自动等同业务依赖。

### 源程序构造（`SourceConstruct`）与实现机制应用（`MechanismApplication`）

保留源语言、语法种类、源码定位、声明形状/签名、源码包含关系。构造类型包括模块、类、字段/属性、函数/方法、枚举/成员、泛型、宏定义/调用/展开、注解/应用、λ 匿名函数/闭包等。

可选的 `ImplementationMapping` 将语义实体/属性/关系映射至一个或多个源码构造，角色可为 `declares`、`implements`、`represents`、`constrains`、`generates`、`invokes`。映射允许多对多、部分、间接、冲突、未解析或不存在已建立映射；源码构造即使没有语义映射也可独立保存与查询。类可以通过成员变量实现数据实体属性、通过成员方法实现多个计算实体；一个语义实体也可以横跨多个类或函数。源码成员依赖保留为实现结构关系，不替代语义属性或子实体关系。

宏、注解、泛型、Lambda 等作为 `MechanismApplication` 或 `SourceConstruct` 类型保留。未观察宏展开/注解处理效果时只记录构造与缺口；不把某机制推广成目标语言迁移时的要求。

### 测试实体（`TestEntity`）与验证关系（`VerificationRelation`）

测试作为语义实体独立标识，包含其可获取的场景、输入、期望/断言、条件及证据。`verifies` 关系指向被测语义实体或独立身份的行为/属性主张（如特定结果或效果约束）；测试入口映射单独指向测试源码构造。测试文件/函数的存在不能自动证明测试覆盖了某个业务目标。

### 事实主张（`FactClaim`）、证据（`Evidence`）与覆盖（`Coverage`）

保留事实断言的谓词、值/对象引用、条件、主张模式、来源/提取方法、证据角色和推导链。将主张认识状态（`confirmed` 已获证据支持、`provisional` 暂定、`conflicting` 冲突）、获取覆盖状态（`obtained` 已获取、`not_acquired` 未获取、`unsupported` 不支持、`not_applicable` 不适用）、响应呈现状态（`included` 已呈现、`not_expanded` 未展开）正交表达；状态不可互相代替。覆盖按实体、谓词族、条件及输入闭包记录。缓存/身份复用依赖项目指纹、分析器/解析器版本、工具版本，以及解释模型/提示版本（若使用）；相关依赖变化时标记过期，并在用户请求时重验。

区别直接源码声明、工具提取、文档陈述、规则推断及运行观察；分析器不裁决证据之外的领域真相。

E0–E4 不再是主实体分类。可对相关事实附一个或多个观察视角（工程/协作、构建/交付、程序/接口、行为契约、算法/局部语义），不因视角给实体重键，也不从视角推实体包含关系。它们保留检索与报告时的有用切面。

## 主要不变量

1. 首次构造语义实体时由持久注册表分配身份并关联到分析范围；同一注册表内重复查询复用注册项。名称、路径、行号、内容摘要、工具节点标识、E视角、语言语法类型均不单独构成 `EntityId`。源码移动/重命名只生成连续性候选；无明确证据或显式映射时保留新旧身份及`continuity_unresolved`（连续性未决）状态，不自动合并。注册表丢失后不保证跨次身份连续，必须报告。
2. 语义实体身份与实现构造身份分离；同一身份的实体类型冲突是契约错误。
3. 单实体详情查询中，实体属性在该实体描述中完整返回；列出直接子实体时只返回身份、名称、类型及可选短摘要，除非请求同时要求其完整描述。子实体通过关系按深度展开，不能因默认非递归而遗漏被选为详情目标的实体属性。
4. 每项语义解释、关系和实现映射必须可追溯到证据或显式标注为待确认；证据冲突保留并报告。
5. 属性类型至少区分语义类型和实现类型；值域必须区分声明、校验、规范和运行观察，未证不得补造。主张认识状态、获取覆盖、查询呈现状态与缓存新鲜度正交。
6. 工具输出解析器负责规范化输出和来源定位；其输出不能直接证明更高层业务解释。语义实体构造需记录从源构造/文档证据到实体主张的推导。
7. 首期获取语言仍为Python和Rust；模型语言无关不代表分析能力覆盖所有语言或平台组合。

## 查询行为

- `项目有哪些语义实体`：返回其直接定义/分组的实体身份、类型、语义名称、短摘要和直接关系；不返回每个子实体的完整属性。
- `模块有哪些数据/计算实体`：默认返回该模块直接实体成员关系和成员的身份、类型、语义名称、短摘要；若请求明确要求这些成员完整描述，再返回每个成员的自身全部属性；均不递归加载成员实体的关联子图。
- `某数据实体的完整描述`：一次返回所有已取得属性（名称、语义类型、实现类型参考、值域、基数、约束、证据和缺口）及直接关系；被引用实体仅返回引用信息。
- `某实体如何实现`：返回映射到的源码构造、机制应用、定位、映射角色、证据和未解析部分；不自动递归展开其被调用者。
- `哪些测试验证某实体`：返回直接验证实体/行为的测试及源码入口关联；未知覆盖必须显式保留。

机器和可读输出应从同一查询结果投影，不能分别推理生成。完整实体描述必须包含所有已取得属性；覆盖不完整时返回已得属性和明确缺口，不能将“完整描述”误作“已证明业务属性穷尽”。

## 实施策略

### 评估过的路径

1. **以语义实体模型替换公共主模型，并保留旧模型档案作为只读兼容端口和确定性导出投影（推荐）**：正式切换后仅新模型档案可写，旧完整档案为只读兼容；切换前旧默认流程保持不变，新档案验证仅写入隔离测试档案/夹具，避免双主写入。旧消费者有迁移窗口；无法表达的关系/属性必须附带损失/缺口诊断，不得静默丢字段；代价是需要版本化契约和显式投影。
2. **同时维护E0–E4旧模型与实体新模型作为并列可写主模型**：短期较易逐项接入；但产生双重身份、事实同步和语义不一致风险，不适合作为最终结构。
3. **只把实体概念叠加为旧事实主体的别名/视图**：改动较小；无法表达属性、源构造、测试与语义实体的独立身份，未满足模型目标。

用户已选择语义实体为中心的重构目标；本设计推荐方案1作为迁移方式。若完整代码审查发现不可兼容约束再呈具体反例，不擅自退回并列主模型。

### 迁移阶段

1. 冻结语义实体、关系、属性值域、来源/状态词汇及版本化公共结构模式；保留E0–E4为事实视角。
2. 增加 `semantic-entity-model` 模型档案、注册表、谓词/类型目录、引用与不变量校验；不复用 `SourceDeclaration` 身份作为语义实体身份。
3. 重构Python/Rust解析适配器：先给出源程序构造与工具证据，再经显式规则/推导创建语义实体候选、属性和映射；保留不确定性。
4. 重构构造器和查询路径；支持实体、属性、子实体关系、实现关系及测试关系的按需获取、存储和投影。
5. 为旧SQLite数据实现受限导入、兼容查询及确定性导出；切换前在隔离测试档案/夹具中验证，不改变旧默认写路径。旧M1仍按既有独立入口读写。仅当存在明确的一一映射规则才生成新实体映射；其余数据保留在旧档案并标记未迁移，不靠名称/路径批量猜测身份。
6. 以真实Python/Rust项目遍历所有新模型支持的语义记录，对照实体标识、属性、关系、证据、缺口，并验证仓储回读、查询、兼容导出、全套测试和成本数据。所有结果通过后，在单独的最终迁移步骤中切换为默认写入新模型档案、旧完整档案只读；M1独立入口不变。

回滚时保留迁移前数据库副本和旧模型档案读取路径；不得把新模型档案写入旧结构模式或反向丢弃证据。产品版本、模型档案版本、SQLite迁移版本分别管理。

## 不在本次目标

- 声称对任意项目完全还原业务意图或自动判定实体划分正确。
- 要求迁移目标语言重复使用上游宏、枚举、泛型、注解等特性。
- 扩大Python/Rust以外的首期语言范围，或假设宿主、工具、项目目标平台天然相同。
- 设计统一服务/聚合部署架构；本领域模型不预设数据库表形状或DDD聚合根。

## 证据与验证

结构模式和领域不变量验证公共模型是否合法；真实项目的完整遍历与仓储回读验证覆盖和数据保真；语言案例验证实现构造的映射差异。它们不证明推导出的语义一定为真。性能、存储开销和实际大语言模型词元用量应在相同输入、请求范围、缺口口径与环境下，与当前路径作前后测量；未测数据不得声称节省。当前环境为共享开发模式，测试与复核应标明身份隔离限制，不能称为私有盲验收。
