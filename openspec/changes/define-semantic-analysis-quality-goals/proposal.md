# Proposal

## Why

#5要求将查询性能、构造成本、Token、正确性和支持范围置于同一可验证口径，避免空结果或缓存命中制造虚假收益。依据：本Issue输入、共享context与battle.json；新评价定义是候选，非用户确认或实测。

## What Changes

- 建立绑定场景、规模、环境、质量和支持组合的评价档案。
- 区分全部请求的结果分布、成功延迟、首结果和完整成功，比较首次/复用/变化的实际Token。
- 必要操作、获取边界与优化前后评价已由用户明确，具体组合由设计落实；负载范围依ADR-0005延期至实际分析测试后确定，不作为当前规划冻结前置条件，本提案不填猜测值。

## Capabilities

### New Capabilities
- `semantic-analysis-scope`: 用户已确认的语言/平台/负载/固定输入及目录/操作边界；仅明确确认项同步基线。
- `semantic-analysis-quality`: 质量、性能和成本的可比评价及证据边界。

### Modified Capabilities

无。

## Impact

关联#6–#13；仅固化用户已确认的语言范围及平台定义主规格，不修改原模型/查询主规格，不实现基准或产品。候选定义待整体审核，ADR-0007已确认需求/评价方式，具体技术设计仍待整体审核。

## 2026-11-02 系统需求确认接续

以ADR-0007及后续“当前一层=符合用户请求要求的顶层语义事实”为用户确认依据；需求与工具/接口等代理设计决定分开。人机双输出、缺口原因、查询触发与同主体补充、必要操作可执行及优化前后自评已明确。需求基线不等于全部设计已批准，当前仍不实施/归档。
