# Design

## Context

当前公共模型档案`semantic-fact-model-1`包含E0–E4语义谓词目录和`SourceDeclaration`主体；Python/Rust获取器按语法种类产生`Fact`记录，投影器将这些记录转换为结构模式记录，SQLite保留M1与完整档案两套写入路径，查询选择器主要针对类/函数等源码类别。详细领域定义见[语义实体中心领域模型设计](../../../docs/superpowers/specs/2026-11-07-semantic-entity-domain-model-design.md)，行为契约见本变更规格增量。

实现须遵守首期Python/Rust范围、共享开发模式、如实披露证据缺口及当前存储/工具选择；不得将语言无关模型宣称为工具支持所有语言。历史ADR-0001/0002记录保留不改写，本次用户明确提出的重构要求通过新ADR取代旧“E0–E4为主组织轴”决定。

## Goals / Non-Goals

**Goals:**

- 建立版本化语义实体profile及公共注册目录，表达项目/模块/能力/数据/计算/外部参与者/测试实体、属性、关系、源码构造、实现映射、验证映射和证据。
- 让所有获取适配器先解析成规范的源码构造与证据，再从构造器生成有依据、可不确定的语义实体主张；同一信息只定义一套类型和身份规则。
- 让查询、按需构造、SQLite持久化、算法视图及双输出均使用同一实体身份和关系模型。
- 避免不必要模型上下文和重复工具执行，同时在同输入/请求/缺口口径下测量实际性能、数据量及LLM token；不预称节省。

**Non-Goals:**

- 不证明所有自动解释的业务含义为真，不生成无证据意图或完整性保证。
- 不自动把既有路径/名称/SourceDeclaration映射成同身份语义实体；不在此变更中扩大语言范围、用户查询自然语言范围以外的承诺或运行时行为覆盖。
- 不将源码设计特性转换为迁移目标的必要设计，不预定DDD聚合、领域服务、六边形架构或存储布局。

## Decisions

### 1. 采用唯一规范实体模型，旧模型档案仅作兼容接口

新增版本化`semantic-entity-model-1`契约，不在`semantic-fact-model-1`与新模型档案之间双写可编辑的语义事实。现有`semantic-fact-model-1`可由兼容读取接口返回，也可通过确定性投影导出；适配期间新模型档案为权威来源。M1项目发现和旧完整数据包保持可读，不自动升级；若身份映射没有规则依据，旧`SourceDeclaration`保持原身份并标记尚无`SemanticEntity`映射。

替代方案是并列双写两个主模型档案；由于会产生身份复制、同步竞争和事实偏差，因此不采用。只在旧记录外增加实体别名也无法表达实体属性/子实体、测试目标和实现构造的独立身份，因此不采用。

### 2. 语义实体与源码构造身份分离，属性默认属于实体描述

所有用户可独立引用的项目/领域对象使用`SemanticEntityRef`；其标识由指定分析范围下的持久注册表首次分配并存储，后续请求复用同一注册。注册项中的`sourceKey`是重新关联证据的查找键，不是实体身份；名称、路径、行号、内容摘要、E视角或工具标识均不能单独生成实体身份。源码移动、重命名或注册表丢失后，只能提出连续性候选；缺少显式映射或强证据时记录`continuity_unresolved`（连续性未决），不得合并。新建或清空注册表不保证跨注册表身份稳定。类型目录管控常用实体类型并保留受控扩展机制。模块和能力是语义分类；Cargo软件包、Python模块和目录是源码/构建构造，通过显式映射表示。

实体自身的`EntityAttribute`作为按实体身份与稳定槽位键引用的类型化描述项，默认不单独注册为`SemanticEntity`。需要被其他实体独立引用时，通过迁移映射提升其身份并保留旧引用，不复制语义主张。`ChildEntityRelation`指向独立实体，避免把实体图递归嵌入属性数据块。单实体详情查询完整返回自身属性；实体清单只返回直接成员引用和简短摘要，除非明确请求成员的完整描述；子实体关联图按请求展开。

### 3. 事实是有证据的主张，E0–E4是可选观察注记

公共谓词目录区分实体身份、实体属性、关系、实现映射、验证映射及来源事实。每条主张记录证据、条件、`claimMode`（主张类型）和获取状态。主张认识状态（例如`provisional`暂定、`conflicting`冲突）、获取覆盖状态（例如`obtained`已获取、`unsupported`不支持）、响应呈现状态（例如`included`已呈现、`not_expanded`未展开）和来源新鲜度分别建模；覆盖按实体/谓词/条件范围登记，项目指纹、分析器/解析器/工具版本及解释模型/提示版本变化会使相关覆盖过期。E0–E4作为事实观察视角保留，可以不标注或多重标注，不作为谓词主体类型或自动包含规则。旧模型档案导出时映射到最接近的旧谓词并保留信息损失/缺口；不能无损表达的字段留在权威新模型档案中。

Cargo workspace成员是E1构建观察，不是默认的语义实体类型。成功取得的成员包名和manifest路径作为Project实体的`workspaceMemberPackage`主张保存，并链接Cargo metadata方法及Cargo.toml摘要证据；包边界不自动等同于业务模块。未请求或工具不可用时分别保留未展开或未取得状态，不伪报空成员集合。

### 4. 工具解析器统一获取证据，语义构造器负责解释映射

工具矩阵按待获取信息的覆盖能力选择工具；每个适配器将特定工具输出解析为共享的`SourceConstruct`/`Evidence`输入契约，不重复定义领域类型。确定性分析先产出声明/结构和工具事实；规则或大语言模型解释须作为带推导链的独立主张，允许未决、冲突和覆盖缺口。宏/注解效果、绑定和动态调用目标仅在工具或证据支持时构造。

### 5. 查询实体时返回完整属性，按明确范围展开子实体

查询请求统一表达目标`EntityRef`、所需描述面（属性、关系、实现、验证、行为等）、直接实体筛选和可选展开界限。单实体详情中的自身属性不受递归界限影响；清单中的子实体默认只返回身份/类型/名称/摘要，明确要求成员完整详情时才获取并返回其属性。默认关联只返回直接关系和实体引用。旧类/函数选择器保留为`SourceConstruct`视图，通过映射查询语义实体，不让源码类别成为新模型的根。

### 6. 分区重构获取、投影、校验和仓储

在`acquisition.py`内从统一源码事实逐步拆分结构解析与实体构造（如需模块重命名，保持命令行接口和程序包接口兼容）；`projection.py`只投影规范构造器的输出，不按源码种类猜测语义种类；`validation.py`根据新目录/结构模式校验身份、属性域、关系端类型、证据、覆盖和迁移映射。`semantic_store.py`增加按模型档案隔离的实体/属性/关系/构造/映射索引与可无损往返的JSON数据块，复用当前规范化与原子事务策略。不得另建工具私有的语义身份/模型。

### 7. 分阶段写入、回读并保留回滚路径

阶段1发布新契约及对照夹具；阶段2生成`SourceConstruct`及其映射；阶段3使构造/查询统一消费实体模型档案；阶段4在隔离模型档案/夹具中实现旧档案兼容读取/导入/导出与SQLite迁移，不改变当前旧档案的默认写入路径。阶段5使用真实项目进行遍历、性能/词元实测，并完成所有查询回读和集成验证。只有这些验证全部通过后，才通过独立最终迁移任务切换命令行接口默认写入新模型档案、旧完整档案只读；M1项目发现入口保持独立。切换前保留快照与回滚记录，旧档案导出必须报告无法表示的属性/关系。任何阶段不得把不兼容的模型档案混写为同一数据包。迁移失败时保持旧文件/表不变并报告兼容缺口；回滚依靠档案隔离及数据库备份，不删除历史证据。

### 8. 验证覆盖与声明边界

契约测试检查结构模式、身份唯一性、类型约束、属性完整、关系闭合和来源可追溯；真实项目遍历逐项对比构造、存储回读、查询响应中的实体/属性/关系/证据标识及缺口代码；Python/Rust各至少覆盖类成员、普通函数、泛型、宏/注解/λ匿名函数/闭包、数据域和测试映射中实际可解析与不可解析案例。跨宿主/目标平台不得虚构已验证矩阵。质量记录区分共享开发测试、公开持续集成与未执行的私有隔离验收。

## Risks / Trade-offs

- **语义实体推断本身不完备** → 将直接证据、派生主张、未定/冲突状态分开，查询报告范围和缺口；不宣称语义真值证明。
- **旧事实无法一一迁移到语义实体** → 兼容读取旧profile；只迁移有明确规则的记录，保留其他内容和证据，输出迁移诊断。
- **实体/关系结构模式和索引增长增加存储/维护成本** → 先用必要类型和请求驱动构造；按真实项目全量遍历测量SQLite体积、查询时间及模型词元用量，保持性能回归可见。
- **语言/工具间同一语法构造含义不同** → 工具适配器只负责语法/输出事实，语义映射使用语言无关谓词且附语言/工具来源；无等价语义时不合并。
- **新profile和旧CLI输出短期并存** → 仅新profile可写；旧CLI通过投影视图兼容并给弃用边界，避免双主写入。
- **共享环境不能证明独立盲验收** → 实施与公开测试可以继续，报告不得将其称为私有验收或双向盲隔离通过。

## Migration Plan

1. 用户审阅并确认此设计后，为主规格增加新模型要求及替代ADR，旧决策记录保留历史。
2. 建立新模型档案契约、结构模式和验证器；完成标准契约夹具与反例，再接入采集器。
3. 逐步改造工具结果解析器、语义实体构造器、命令行查询和报告；每阶段保留旧入口，但统一内部身份引用。
4. 扩展SQLite模型档案注册表、表/索引、规范化器和原子读回；迁移时创建备份，只转换身份映射有证据支持的记录。
5. 使用固定真实Python/Rust项目遍历已支持事实，比较来源证据、迁移缺口、仓库回读和词元/资源指标；通过后将旧完整模型档案标记为只读兼容。
6. 如果新模型档案验证失败，停止写入新档案并恢复兼容读取；不删除或覆盖旧数据包，修复后重新执行迁移。

## Open Questions

无。实现细节均可按此设计及现有ADR-0011共享开发授权落实，不改变用户可观察的模型方向或任务边界。

## ADR-0013 当前约束（2026-11-08）

保留语义实体、属性、关系、源码构造、证据及测试映射；取消DDD解释。既有实现和切换任务记录保留其原证据，新目标下的实现差距须另行核对，不因旧任务完成自动通过。 依据：`docs/decisions/0013-非DDD语义事实模型.md`。历史执行记录中的DDD或旧模型表述不构成现行约束。本轮只进行文档修订，产品重构完成状态不变。
